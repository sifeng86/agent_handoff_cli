# Doppler write-contract investigation

Historical strict-writer investigation. The user subsequently approved basic synchronous Doppler writes and current-state confirmation; provider fencing/CAS/terminal APIs below are no longer release prerequisites. See the revised [specification](spec.md#14-doppler-backend-capability-gates) and [recovery behavior](secret-recovery.md). Retain this document as context, not an active blocker.

Read-only contract review performed 2026-10-14. No Doppler CLI authentication, API request, or write was performed. The scope is the A44/A46 contract in Design v1.2 §15.9–15.10, §20.8 and §22, compared with this repository's current adapter boundary.

## Findings

| Required property | Publicly documented contract reviewed | Evidence status for this runtime |
| --- | --- | --- |
| A44: upload only the selected local key, verify the remote value, then advance baseline | The [Secrets Update API](https://docs.doppler.com/reference/secrets-update) documents `POST /v3/configs/config/secrets` with `project`, `config`, and either a `secrets` object or `change_requests`, returning HTTP 200. The [CLI setting guide](https://docs.doppler.com/docs/setting-secrets) documents setting one or more keys, including stdin, and recommends `--silent` when output is captured. | A key-targeted mutation is documented at the API/CLI level. The reviewed pages do not establish expected-old-value compare-and-set, mutation fencing, idempotency/operation identity, or an authoritative per-operation terminal-status query. Thus a successful response plus a later read is not yet a proven safe terminal contract for this runtime. |
| A46: merge different local and remote keys without losing either change | The update endpoint accepts a `secrets` object; the CLI guide supports setting one or more keys. Doppler's [Secrets documentation](https://docs.doppler.com/docs/secrets) says changes to other environments cascade only the properties changed, similar to PATCH. That statement concerns cross-environment cascading, not a conditional same-config update contract. | Public docs reviewed do not specify same-config omitted-key behavior under concurrent writes or a config revision precondition. Per-key sequencing and reread can detect some races, but cannot prove a stale request will not later overwrite another writer. A46 remains unverified for the required concurrency guarantee. |
| A44/A46: a Git-fenced session remains fenced at the provider mutation | The [API authentication reference](https://docs.doppler.com/reference/api) documents CLI and personal tokens with account-wide read/write access and service tokens with access scoped to a config. The [Update API](https://docs.doppler.com/reference/secrets-update) describes project/config targeting. | The reviewed contract describes credential/resource scope, not a lease or session token checked by the provider at each secret write. It does not prove that a request already in flight from a formerly valid session is rejected after Git ownership changes. Absence from these pages is not proof Doppler cannot offer such a facility; it is an unverified prerequisite. |
| Timeout/partial result: distinguish terminal acceptance/rejection from unknown | The update reference documents an HTTP 200 response. Doppler's [Activity Log schema](https://docs.doppler.com/docs/activity-log-event-schema) documents `enclave.project.config.secrets.update` events with change diff metadata; [Versioning](https://docs.doppler.com/docs/versioning) describes history and rollback for secret changes. | Reviewed docs do not define a client-supplied operation ID with a durable status lookup, replay/idempotency behavior, or a terminal receipt covering a timed-out request. Audit/history records are useful observations but are not documented as a synchronous, correlated terminal-status API. Until a request is proven terminal, this runtime must retain `unknown/pending` and must not replay or advance B. |
| Different-key merge: preserve an independent remote edit while applying a local edit | The list endpoint supports selecting secrets by name; update accepts a secrets object. | These are useful scope controls, but docs reviewed do not provide an atomic read-modify-write or expected-config-version guard that proves two concurrent actors cannot replace one another's changes. Merge semantics and conditional behavior need authoritative clarification or a documented contract before enabling the writer. |

## Repository boundary

`src/agent_handoff/secrets/doppler.py` implements scoped reads only. `Adapter.capabilities` defaults `strong_writer_fencing`, `conditional_key_write`, and `terminal_write_evidence` to false; `Adapter.require_write_gate()` rejects upload unless all are verified. `Doppler` does not override write/lease/status operations. `SecretService._apply_locked()` requires the gate before lease or remote mutation and records per-key operation evidence; its baseline advancement follows verified writes. This is consistent with the current evidence: read-only Doppler evidence does not establish A44/A46 writer safety.

## Required next step

Keep production uploads disabled. Obtain an authoritative Doppler contract answer (vendor documentation or written vendor confirmation) for all of the following before implementing a writer: a provider-checked fencing token that invalidates stale sessions at mutation time; per-key expected-value or config-revision conditional updates with documented behavior for concurrent different-key edits; and durable operation identity/status or another documented terminal receipt with timeout and retry semantics. If any property is unavailable, record that limitation and redesign the product contract before considering a reduced write mode. Do not use a disposable project as a substitute for these guarantees: a staging test can characterize behavior, but cannot protect a real config from an in-flight stale request.

## Official CLI source follow-up

On 2026-10-14, GPT-6-Luna reviewed official docs and CLI source; Primary independently checked the [Update API](https://docs.doppler.com/reference/secrets-update) and [`pkg/http/api.go`](https://raw.githubusercontent.com/DopplerHQ/cli/master/pkg/http/api.go), function `SetSecrets`. This client chooses `secrets` or `change_requests`, targets project/config, sends a bearer-authenticated POST, and parses the returned secrets. Its request construction supplies no expected revision/value, session fence or client operation identifier. The download function's conditional cache header is a read optimization, not a conditional mutation guarantee. `master` is mutable; this observation is dated, not a version-pinned product guarantee.

This narrows the finding to a concrete client path; it does not establish whether the server offers another documented facility. No credential access, Doppler API call, secret write or model turn was performed. The remaining prerequisite is a vendor contract answer, rather than another local mutation test. [Draft vendor questions](doppler-writer-contract-questions.md) specify the required race and timeout semantics; they have not been sent.
